# Changelog

Notable changes to tf-eu-guard. Entries follow
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) conventions; the
registry has changed in ways worth tracking beyond commit messages
(new provider registries, custom checks ported to Kubernetes, the
terraform_plan fix), so this starts now rather than reconstructing
history later. Versions follow the git tags/`__version__` at each
release point.

## [Unreleased]

### Added

- `tools/generate_checkov_coverage.py --check` also fails on an `intentionally_unmapped` or `known_stale` triage ID that
  Checkov no longer defines (a `known_stale` ID a registry still maps stays allowed), and takes `--doc PATH`. New report
  goldens cover a second input (mapped, unmapped and inline-suppressed findings) with `--show-unmapped` and with an object
  `--baseline`, in every output format (TEG-17).
- Machine outputs count baselined unmapped findings: the `--counts-file` gains `baselined_unmapped=N` after `baselined=`, the
  Action gains the output `baselined-unmapped`, and the Markdown summary line ends with `Baselined unmapped: N`. The
  auditor report says known unmapped findings are counted, not listed, unless `--show-unmapped` is set (TEG-10).
- `docs/checkov-coverage.md`, generated by `tools/generate_checkov_coverage.py` for the pinned Checkov release: every
  Terraform and Kubernetes check as mapped, intentionally unmapped (reasons in `tools/checkov_triage.yaml`) or untriaged.
  CI runs `--check`, which also fails on a registry ID that Checkov no longer ships (TEG-10).
- Emulator tier: a failed `terraform` call now raises `TerraformError` carrying its stderr tail, the `endpoint` fixture fails
  with the LocalStack start command when the health check does not answer, and Terraform runs with the AWS config and
  credentials files pointed at `/dev/null`. The Azure/GCP region snapshot loader rejects non-list or non-string entries (T-29).
- `--unmapped-severity SEVERITY` (config key `unmapped_severity`, Action input `unmapped-severity`) counts every
  active unmapped Checkov finding as a finding of that severity for `--fail-on-severity` and `--fail-on-any`.
  Reports are unchanged and the default gate is unchanged (TEG-10). Unmapped findings are never waived;
  `--baseline` covers them (see Changed), so only new ones count; use an inline `checkov:skip` to exempt one.
- Action input `json-format` (`array` or `object`, default empty) passes `--json-format`, so Action users can silence the
  implicit-default deprecation warning.
- The gate "Fail:" line names the threshold as `ANY` whenever `--fail-on-any` is set, also together with `--fail-on-severity`.
- `--fail-on-severity`, `--fail-on-any` and `--fail-on-unmapped` help, the README, limitations and architecture docs now
  mention `--unmapped-severity`.
- A Terraform scan warns on stderr when `google_*` resources were scanned but no `EUGUARD_POLICY_004` result
  appeared, because the region then comes from the environment (for example `GOOGLE_REGION`) or the provider at apply
  time; same semantics as the AWS region-unset warning.
- Opt-in emulator test tier (`tests/emulator/`, `TFEG_RUN_EMULATOR=1`) and a CI job `emulator` that run real Terraform
  against a digest-pinned LocalStack 4.9 service: an environment-supplied region is caught in plan mode
  (`EUGUARD_POLICY_002`, `EUGUARD_GDPR_003`), and an applied S3 bucket is read back through boto3 and compared
  with `CKV_AWS_53` to `56`. The default suite skips it.
- GCP residency: `EUGUARD_POLICY_004` (`provider "google"` `region` and `google_*` resource `region`, `location` and
  `zone` within the configured residency policy) and `EUGUARD_GDPR_005` (known third-country location, a hedged
  Chapter V review signal). The policy check is fail-closed against a maintained EU/EEA table (zones map to their
  region; dual-regions such as `EUR4` are not yet verified and fail); the Chapter V check fails only for known
  third-country locations, London, Zurich and the `US`/`ASIA` multi-regions included. `eusc` uses the GCP EU/EEA
  table (TEG-05).
- Azure residency: `EUGUARD_POLICY_003` (resource `location` within the configured residency policy) and
  `EUGUARD_GDPR_004` (known third-country location, a hedged Chapter V review signal) cover every
  `azurerm_*` resource. The policy check is fail-closed against a maintained EU/EEA location table; the
  Chapter V check fails only for known third-country locations, the UK and Switzerland included. The shared
  `POLICY RESIDENCY-001` article title is now "Region residency policy" (TEG-05).
- Action input `fail-on-unmapped` (default `false`) passes `--fail-on-unmapped`, so a workflow can fail on active
  Checkov findings that have no EU mapping (TEG-10).
- A Terraform scan warns on stderr when a local module `source` (`./` or `../`) resolves outside the scan
  root, where Checkov still reads and reports those files beyond the symlink boundary (TEG-08). Exit codes
  are unchanged.
- A replaced `hcl2` module (another package such as python-hcl2 overwriting Checkov's bc-python-hcl2 in the
  same environment) is reported as a Checkov runtime error (exit 3) that names the cause and the fix, instead
  of a raw `ImportError` traceback from the Checkov subprocess (TEG-14). The probe runs inside the Checkov
  subprocess before `checkov.main` is imported (it exits 97), so it covers every IaC type including Kubernetes
  and sees the same `sys.path` Checkov does.
- `--no-discovery` (and `scan(no_discovery=True)`) skips `.tf-eu-guard.yaml` and
  `.tf-eu-guard-waivers.yaml` in the scan root, so a pull request cannot weaken its own gate by
  committing them; `--config` and `--waivers` still apply and each ignored file is named on stderr
  (TEG-01).
- `--max-waiver-days N` (config `max_waiver_days`, `scan(max_waiver_days=)`, Action input `max-waiver-days`)
  refuses waivers that expire more than N days ahead, so their findings stay active, and a waiver without a
  `file` pattern now warns that it matches the resource in every file (TEG-01). Opt-in; exit codes are
  unchanged unless the option is set.
- A Terraform scan warns on stderr when AWS resources were scanned but no `provider "aws"` block sets a
  region (the residency checks cannot tell where they deploy), and a directory scan warns when hidden
  directories such as `.prod/` hold source files that Checkov skips (TEG-05). Exit codes are unchanged.
  The region warning also fires on a live scan with no `provider "aws"` block, where every EUGUARD check is
  UNKNOWN and no EUGUARD result exists; only `--checkov-json` input stays silent without one.
- `provenance.commit` is no longer null in the Action: the Action resolves the scanned checkout's HEAD on the
  runner (`git rev-parse HEAD` in the scanned directory; on `pull_request` that is the merge commit) and
  passes it as `TF_EU_GUARD_COMMIT`, falling back to `GITHUB_SHA` when that directory is not a repository.
  The value is used when git is unavailable and it is a 40- or 64-character lowercase hex id, and the new `provenance.commit_source` (`git`, `environment` or null) says which
  one supplied it (TEG-13).

### Changed

- Source scans of GCP stacks where no `provider "google"` block and no `google_*` resource sets a region or location now
  report one MEDIUM finding, `EUGUARD_POLICY_006` (`provider.google`), next to the existing stderr warning; `--checkov-json`
  input that contains tf-eu-guard custom-check results gets it too. The Action's default gate (HIGH) is unaffected, while
  `--fail-on-severity MEDIUM`, `LOW` or `INFO` and `--fail-on-any` now fail. `--framework nis2` or `gdpr` drops it (it
  carries a POLICY article). Existing `--baseline` files do not contain it, so a MEDIUM-or-lower gate with a baseline
  fails once on upgrade until you re-baseline or waive it. Reusable module repositories always get it: waive
  `EUGUARD_POLICY_006` on resource `provider.google` (no file), or scan the root module or plan; an inline
  `#checkov:skip` has no effect. Plan scans are unchanged. The AWS and GCP injections now share one loop (TEG-05).
- Source scans of AWS stacks where no `provider "aws"` block sets a region now report one MEDIUM finding,
  `EUGUARD_POLICY_005` (`provider.aws`), next to the existing stderr warning; `--checkov-json` input that contains
  tf-eu-guard custom-check results gets it too. The Action's default gate (HIGH) is unaffected, while
  `--fail-on-severity MEDIUM`, `LOW` or `INFO` and `--fail-on-any` now fail. `--framework nis2` or `gdpr` drops it (it
  carries a POLICY article). Existing `--baseline` files do not contain it, so a MEDIUM-or-lower gate with a baseline
  fails once on upgrade until you re-baseline or waive it. Plan scans are unchanged (TEG-05).
- `EUGUARD_POLICY_005` no longer treats a module named `aws_bridge` (or `google_*`) as an AWS (or GCP) resource: only the
  resource-type segment is matched, so a GCP-only stack that wraps resources in such a module gets neither the finding
  nor the AWS warning. With `--download-external-modules` the finding is anchored in a root-module file when one
  exists, not in `.external_modules/`.
- `tools/generate_checkov_coverage.py --doc` as the last argument now exits with a clear message instead of an
  `IndexError`; the `--counts-file` help lists `baselined_unmapped`.
- `--baseline` now matches unmapped Checkov findings (check ID, resource, file path) against the baseline's
  `unmapped[]` and `baselined_unmapped[]` (entries flagged `suppressed` and array-format baselines give none). Known
  unmapped findings move out of `unmapped` into the new JSON object array `baselined_unmapped` (same entry shape;
  required by the schema, which stays at `schema_version: "3"` because 3 is unreleased), so the gate,
  `--fail-on-unmapped` and `--unmapped-severity` see only new unmapped findings, and `--changed-since` filters the
  new group too. The scan-settings line reads `baseline: FILE (DATE, N known finding(s) matched, M unmapped)` (shown on stderr only for array JSON and CSV output, otherwise inside the report). Known unmapped
  findings stay visible in every report like known mapped ones: SARIF results carry `baselineState: "unchanged"` (active
  unmapped results become `"new"` when a baseline is used, except with an array baseline, which cannot record unmapped
  findings and leaves them without a `baselineState`), CSV rows get status `baselined`, and the dev, security,
  developer-HTML and auditor reports show a "Known unmapped (in baseline)" count (rows with `--show-unmapped`) and no longer
  show the clean "No compliance findings" state when only known unmapped findings remain. Waivers still never cover unmapped
  findings (TEG-10).
- `--baseline` matches a finding against the baseline's mapped and unmapped entries together, so a check that a
  registry overlay or upgrade maps (or unmaps) between scans stays known instead of failing the gate. An array
  baseline cannot record unmapped findings: stderr says so once, unmapped findings count as new unless the baseline
  recorded the same check as a mapped finding, and SARIF no longer marks unmatched unmapped results
  `baselineState: "new"` in that case.
- `--fail-on-unmapped` (CLI help, Action input and README) now says that with `--baseline` only unmapped findings
  not in the baseline count.
- When `--fail-on-unmapped` and `--unmapped-severity` both trip on the same unmapped findings, the gate prints one
  `Fail:` line (the `--fail-on-unmapped` one) instead of two.
- `provenance.options.json_format` records the resolved layout (`array` or `object`) whenever the output is `json`,
  also when `--json-format` was not given.
- `--output json` without `--json-format` now prints a one-line deprecation warning on stderr (TEG-17). The layout stays the
  deprecated `array`, stdout is unchanged and still a bare JSON list, and the exit code is unaffected. Pass
  `--json-format object` (recommended) or `--json-format array` to silence it; the default changes to `object` in a
  future release. `--output all` writes no JSON report and does not warn.
- The release workflow builds the image locally and scans it with the pinned trivy (fixable HIGH and CRITICAL,
  `.trivyignore.yaml`) before pushing to GHCR; a finding fails the job and blocks the push.
- JSON object schema v3 (`schema_version: "3"`): adds `provenance.commit_source`. The v2 schema closed
  `provenance`, so a v0.9 validator rejects the new key; consumers that check `schema_version` must accept
  "3". `--baseline` and `diff` still read "1", "2" and "3" reports.
- The Action no longer auto-discovers `.tf-eu-guard.yaml` or `.tf-eu-guard-waivers.yaml` in the scanned
  directory: it passes `--no-discovery` unless the new `discover-config` input is `true`. Use `config`
  or, on pull requests, `trusted-config` instead (TEG-01). Behaviour change for workflows that relied on discovery.
- A gated `--checkov-json` scan (`--fail-on-severity`, `--fail-on-any`, `--fail-on-suppressed` or
  `--fail-on-unmapped`) now exits 3 when the file is empty or incomplete (no positive integer
  `summary.resource_count`: missing summary, missing key, a string, a boolean or 0), so a truncated or
  empty file cannot pass a gate; a forged file with a positive count can still pass, since the gate is only
  as trustworthy as the file's producer. `--allow-partial` keeps the warning and ungated runs only warn
  (TEG-09). A file with no `EUGUARD_*` result only warns, since the residency checks need a region or location in the source (AWS, Azure or GCP), so region-less input legitimately has none.
- The encryption-at-rest checks for data stores (`CKV_AWS_16`, `CKV_AWS_3`, `CKV_AWS_96`, `CKV_AWS_5`,
  `CKV_AWS_44`) now all have severity HIGH; `CKV_AWS_96`, `CKV_AWS_5` and `CKV_AWS_44` were CRITICAL, so
  `--fail-on-severity CRITICAL` no longer fails on them. `CKV_AWS_288` no longer cites GDPR
  Art. 4(12) and Art. 33 (a finding is a possible exfiltration path, not a breach). Checkov `CKV2_AWS_27`
  (Postgres RDS cluster query logging) and `CKV2_AWS_34` (unencrypted SSM parameter) are now mapped (TEG-11).
- Severity rubric (TEG-11), written down in `docs/severity-rubric.md` and pinned by `tests/test_registry_rubric.py`
  for public exposure (CRITICAL), public-network guardrails (HIGH), data-store encryption at rest (HIGH) and
  customer-managed keys (MEDIUM). Three checks are raised, HIGH to CRITICAL: `CKV_AWS_24` (SSH open to the
  world), `CKV_AWS_25` (RDP open to the world) and `CKV_AWS_38` (EKS public endpoint open to 0.0.0.0/0).
  `CKV_AZURE_59` (storage-account public-access switch, the counterpart of the S3 block-public settings) is
  lowered from CRITICAL to HIGH. Seven are lowered, HIGH to MEDIUM, because the data is already encrypted with
  a provider-managed key and a customer-managed key (CMK) adds key-control depth that GDPR Art. 32(1)(a) does
  not itself require: `CKV_AWS_119`, `CKV_AWS_147`, `CKV_AWS_149`, `CKV_AWS_247`, `CKV_AWS_327`,
  `CKV_AWS_347` and `CKV_AWS_35`. The risk texts of the 12 CMK-family checks no longer say a CMK is required.
  Gate effect: `--fail-on-severity critical` now also fails on `CKV_AWS_24`, `CKV_AWS_25` and `CKV_AWS_38`
  and no longer fails on `CKV_AZURE_59`; `--fail-on-severity high` no longer fails on the seven lowered CMK
  checks. To restore the previous levels, use `severity_overrides` in `.tf-eu-guard.yaml`:

  ```yaml
  severity_overrides:
    CKV_AWS_24: HIGH
    CKV_AWS_25: HIGH
    CKV_AWS_38: HIGH
    CKV_AZURE_59: CRITICAL
    CKV_AWS_119: HIGH
    CKV_AWS_147: HIGH
    CKV_AWS_149: HIGH
    CKV_AWS_247: HIGH
    CKV_AWS_327: HIGH
    CKV_AWS_347: HIGH
    CKV_AWS_35: HIGH
  ```

- `CKV_GCP_18` (GKE control plane reachable from 0.0.0.0/0) moves from HIGH to CRITICAL: it is the same control as
  `CKV_AWS_38`, and the same control on two clouds belongs to the same severity-rubric family. Gate effect:
  `--fail-on-severity critical` now also fails on `CKV_GCP_18`; restore the old level with
  `severity_overrides: {CKV_GCP_18: HIGH}`. The `CKV_AWS_173` risk text is hedged like the other CMK-family checks
  (the variables are already encrypted with a provider-managed key); see the follow-up entry below for its severity.
- Severity-rubric follow-up (TEG-11). `CKV_AWS_173` (Lambda environment variables), `CKV_AWS_145` (S3 default
  encryption), `CKV_AWS_136` (ECR), `CKV_GCP_38` (Compute Engine disks) and `CKV_AWS_26` (SNS topic) move from HIGH to MEDIUM: the provider
  documentation states each service encrypts at rest by default (for SNS: "By default, Amazon SNS stores messages and
  files using disk encryption"), so they join the customer-managed-key family and their risk texts are hedged
  (`CKV_AWS_173`'s was already). A new family, web port open to the
  internet (MEDIUM), holds `CKV_AWS_260` (already MEDIUM) and `CKV_AZURE_160` (HIGH to MEDIUM): a public web tier
  on port 80 is often intended, and the admin ports are already CRITICAL. Gate effect:
  `--fail-on-severity high` no longer fails on `CKV_AWS_173`, `CKV_AWS_145`, `CKV_AWS_136`, `CKV_GCP_38`,
  `CKV_AWS_26` and `CKV_AZURE_160`. To restore the previous levels, use `severity_overrides` in `.tf-eu-guard.yaml`:

  ```yaml
  severity_overrides:
    CKV_AWS_173: HIGH
    CKV_AWS_145: HIGH
    CKV_AWS_136: HIGH
    CKV_GCP_38: HIGH
    CKV_AWS_26: HIGH
    CKV_AZURE_160: HIGH
  ```

- Azure residency: `belgiumcentral` (Brussels) and `denmarkeast` (Copenhagen), listed as generally available on
  Microsoft Learn (verified 2026-11-27), join the EU/EEA allowlist; `finlandcentral` and `greececentral` stay off it
  and fail the policy check until they are verified. The Chapter V tables now also classify the remaining generally
  available third-country Azure locations and GCP `northamerica-south1` and `asia-southeast3`, so
  `EUGUARD_GDPR_004` and `EUGUARD_GDPR_005` no longer stay silently unknown for them.

### Fixed

- GCP provider-block residency checks (`EUGUARD_POLICY_004`, `EUGUARD_GDPR_005`) also cover `provider "google-beta"`.
- `docs/limitations.md` and the README scope table no longer say plan-mode residency is not covered: the resource-level
  residency checks run in plan mode, the provider-block checks do not.
- `--framework` filtering returns new findings instead of rewriting `articles` and `risk_explanation` on the
  caller's objects, so findings returned by `scan()` no longer change under the caller (TEG-17).
- The unset-AWS-region warning is no longer printed when the Checkov output holds no `EUGUARD_*` result at
  all (the custom checks did not run, so the claim cannot be made) (TEG-05).
- The hidden-directory warning no longer follows symlinked hidden directories, also ignores
  `.terragrunt-cache`, `.mypy_cache`, `.pytest_cache`, `.ruff_cache` and `.circleci`, and applies
  `--exclude` inside the hidden directory too (TEG-05).
- `--max-waiver-days` lists a too-long waiver as "not applied" only when it decided the outcome: a finding
  that another in-range waiver covers no longer produces the warning (TEG-01).
- The Action accepts `path: ${{ github.workspace }}` (the bare workspace, no trailing slash) and the same
  value for its other workspace inputs; it was rejected as an absolute path outside the workspace.
- `--changed-since` keeps Terraform findings in the module directory, parent directories and
  subdirectories of a changed `.tf`, `.tfvars`, `.hcl`, `.tfvars.json` or `.tf.json` file, so changing a variable default no
  longer hides the resources it affects in untouched files; other IaC types stay file-granular (TEG-02).
- Documentation no longer says scanned code is only read and never executed (Checkov evaluates
  Terraform expressions), that `--var-file` is unsupported, or that residency checks cover Azure and GCP;
  the registry typo "weakensing" is fixed (TEG-05, TEG-07, TEG-11, TEG-12).

### Security

- Checkov now runs with an allowlisted environment (`PATH`, `HOME`, locale, proxy and CA-bundle variables,
  the Windows essentials) instead of a denylist, so configuration variables added by new Checkov releases
  (`CKV_*`, `CHECKOV_*`, `BC_*`, `PRISMA_*`, `GIT_*`, `PYTHON*`) never reach it (TEG-16).
  `CHECKOV_TERRAFORM_ALLOWED_MODULE_PREFIXES` and `VCS_ALLOWED_HOSTS` are always passed on (they only
  restrict module downloads); with `--download-external-modules` the module-download credentials
  (`TF_REGISTRY_TOKEN`, `TFC_TOKEN`, `GITHUB_PAT`, `VCS_*`, `BITBUCKET_*`, `SSH_AUTH_SOCK`, and Checkov's
  own proxy settings `PROXY_URL`, `PROXY_CA_PATH`, `PROXY_HEADER_KEY`, `PROXY_HEADER_VALUE`) are passed too.
  `ALL_PROXY`/`all_proxy` are always passed on, like the other proxy variables.
- The Docker base image digest is refreshed (python:3.12-slim, fewer HIGH OS CVEs) and CI gets an
  `image-scan` job that builds the image and fails on fixable HIGH or CRITICAL vulnerabilities with a
  pinned, checksum-verified trivy; the one remaining fixable CVE is a dated exception in
  `.trivyignore.yaml` (TEG-06).
- The Action's `provenance.commit` lookup can no longer be redirected: `git rev-parse` runs with the
  inherited `GIT_*` variables removed and `safe.bareRepository=explicit` (a bare repository planted under
  the scanned path is ignored), and the HEAD is used only when the repository's top level is the workspace
  or inside it; otherwise `GITHUB_SHA` is the fallback. Test git helpers also drop `GIT_*` from their
  environment.
- The Action merges the container's stderr into stdout and wraps both in a random
  `::stop-commands::` token that is resumed after the scan, so workflow commands printed by the
  scanned code are not interpreted while the container runs (TEG-03).
- Terminal and stderr output escapes control characters (newline, ESC, C1, bidi overrides) in
  resource names, file paths, check text, waiver fields, weakening lines and module sources taken
  from the scanned checkout, so a crafted name can no longer forge `::error::` annotations in a
  GitHub Actions log or repaint the terminal (TEG-03). Values are escaped, never dropped. The same
  applies to untrusted CSV columns, Markdown output, and relayed Checkov stderr (indented and escaped
  per line); Rich no longer expands `:emoji:` codes inside names.
- The Action fails with exit 3 if it cannot create a 32-hex stop-commands token, instead of running
  the container unbracketed.
- The Action validates the `path` and `checkov-json` inputs like `config`, `waivers` and `baseline`: a
  `..` segment or an absolute path outside the workspace exits 2, and workspace-relative values are
  passed to the CLI as `$GITHUB_WORKSPACE/<path>` (TEG-15).
- The Action verifies the build-provenance attestation of the image it pulls by tag (`gh attestation
  verify`, signed by `publish.yml`) and runs it by digest; if the pull, digest lookup or verification
  fails it builds the image locally and the notice names the failed stage (pull, digest, gh missing or
  attestation; gh's own output is not printed). New input `verify-image` (default true) turns this off
  only for an explicit `false`, `0` or `no` (any case); a typo keeps it on. An explicit `image` input is
  unchanged (TEG-04).

## [0.9.0] - 2026-11-18

### Added

- Python API: `tf_eu_guard.scan(...)` returns a typed `ScanResult` (findings, requirements,
  provenance) without printing to stdout or exiting; the package ships `py.typed`. The CLI and the API share
  one argument and scan pipeline (`prepare_scan_args`, `run_scan`).
- Provenance: the JSON object gains `provenance` (tool and Checkov versions, registry SHA-256 and
  files, git commit (HEAD; uncommitted changes are not detected), effective options, resources scanned, check counts) and the
  auditor report a "Provenance" section. New `--evidence-dir DIR` writes `dev.html`,
  `security.html`, `auditor.html`, `report.json`, `report.sarif`, `summary.md` and a
  `manifest.json` with a SHA-256 per file; it refuses an existing non-empty directory (exit 2).
- GitHub Action: new inputs `config`, `trusted-config` (read-only mount from outside the checkout,
  so a pull request cannot change the settings in it; keep it self-contained, because files it references must be in the workspace and are controlled by the pull request, and inline `checkov:skip` comments still remove findings unless `fail-on-suppressed` is set), `waivers`, `baseline` and `job-summary` (default
  `true`, appends the Markdown summary to the job summary); new outputs `critical`, `high`,
  `medium`, `low`, `info`, `unmapped`, `suppressed`, `waived`, `baselined` and `total`.
  `trusted-config` must be outside the workspace. Symlinks planted by the scan container are
  never followed or copied back.
- An explicit `--config FILE` now disables `.tf-eu-guard-waivers.yaml` auto-discovery, so a
  trusted config cannot be undercut by a waiver file in the scanned code (`--waivers` and the
  config's `waivers:` key still apply).
- `--output markdown` (summary) and `--output csv` (one row per finding and article; formula-like
  cells are prefixed with `'`), to stdout or `--output-file`. `--summary-file FILE` writes the
  Markdown summary and `--counts-file FILE` writes `key=value` counts (critical..info, unmapped,
  suppressed, waived, baselined, total) in addition to any `--output`, without changing stdout.
- `--secrets` adds Checkov's `secrets` framework (Terraform, Terraform plan, Kubernetes and
  `--checkov-json`). New `registry-secrets.yaml` maps the 19 `CKV_SECRET_*` checks Checkov 3.4.5
  names to NIS2 Art. 21(2)(e) and GDPR Art. 32(1)(b), HIGH. Secret values, code excerpts and
  Checkov's secret hash are dropped on load and never reach any report; parsing errors in the
  secrets scan fail closed.
- `--var-file FILE` (repeatable; config key `var_files`) passes Terraform variable files to
  Checkov so `var.*` values resolve. `--download-external-modules` lets Checkov fetch remote
  modules (stderr note; not available in the GitHub Action's `--network none` container).
  Both are Terraform source scans only; a missing var file exits 2.
- `--changed-since REF`: report only findings in files changed since a Git ref (committed
  and staged; unstaged and untracked changes are not included); hidden findings are counted on stderr and in the scan settings. Not
  valid with `--checkov-json` or `terraform_plan`.

  0 findings while unit tests and CI stayed green because the CI smoke
  step scanned a hand-shaped fixture instead of the real example.
- **Claude Code PostToolUse hook** (`tools/hook_smoke_dispatch.py`):
  maps an edited file to the IaC types it can affect and runs only
  those smoke checks after each edit.
- `docs/check-mapping-table.md` documents the
  mapped-vs-deliberately-unmapped methodology.

### Changed

- Python 3.14 added to the CI test matrix.

## [0.2.1] — 2026-09-05

**Bugfix & hooks.**

### Fixed

- **`terraform_plan` scan path** (`checkov_runner.py`): plan scans now
  run Checkov against the real plan file (`checkov -f <plan.json>
  --framework terraform_plan`) and findings report `file_line_range:
  [0, 0]` (the plan is one JSON line) with reports omitting the line
  reference in that case. The earlier silent-0 failure mode is covered
  by regression tests and the smoke baselines introduced in 0.2.2.

### Added

- `--checkov-json` now accepts multi-check-type Checkov output (a JSON
  array) and extracts the `terraform` result automatically.
- CONTRIBUTING.md sections on smoke checks and the Claude Code hook.

## [0.2.0] — 2026-09-01

**Terraform plan scanning, Kubernetes support, and the Azure/GCP/K8s
registries.**

### Added

- **Terraform plan JSON scanning** (`--iac-type terraform_plan`):
  catches configuration as it will actually be applied
  (`terraform show -json` output). Reuses the same `CKV_AWS_*` registry
  IDs as source mode. Committed example fixture at
  `examples/vulnerable-aws-plan/`.
- **Kubernetes manifest scanning** (`--iac-type kubernetes`): the
  `CKV_K8S_*` namespace gets its own registry
  (`tf_eu_guard/mapping/registry-kubernetes.yaml`, 24 mappings — pod
  security context, RBAC, NetworkPolicy, secrets, resource limits,
  image hygiene, probes). Custom check `EUGUARD_NIS2_001` (hardcoded
  secrets) ported to Kubernetes via Checkov's external-check mechanism.
- **Azure and GCP registries** (`registry-azure.yaml` 23 mappings,
  `registry-gcp.yaml` 22 mappings) — the registry is glob-loaded per
  namespace, so no loader change was needed (`docs/DECISIONS.md` #8–9).
- GitHub Action publish workflow; vulnerable/compliant Kubernetes
  example fixtures.

## [0.1.0] — 2026-08-30

**Initial release.**

- Historical Checkov 3.3.13 wrapper (pinned for reproducible scans at the
  initial release; current releases pin Checkov 3.3.29) with
  enrichment against the NIS2 Art. 21(2) / GDPR Art. 32(1) mapping
  registry.
- AWS registry: 116 `CKV_AWS_*`/`CKV2_AWS_*` mappings, article
  citations verified against the directive/regulation text.
- Custom checks: `EUGUARD_GDPR_001` (non-EU provider regions → GDPR
  Chapter V / Art. 44), `EUGUARD_NIS2_001` (hardcoded secrets →
  Art. 21(2)(e) secure development).
- Report formats: dev (terminal), security dashboard (HTML), auditor
  article-by-article matrix (HTML), JSON.
- `--checkov-json` for pre-generated Checkov output, `--framework`
  filter, `--fail-on-severity` / `--fail-on-any` CI gating.
